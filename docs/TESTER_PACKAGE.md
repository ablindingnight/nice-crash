# Tester package

A copy of Nice Crash someone else can run on their own Windows PC with their own disc. Made by
`tools/package/make_package.py`; the tester's side is `tools/package/README_TESTER.txt` (shipped as `README.txt`).

## The rule

The package contains **no Nintendo data**: no disc files, no `main.dol`, nothing generated from them.

**Since 2026-11-23 releases ship the game ready-made** (`make_package.py --prebuilt --dol <main.dol> --disc <DATA>
--zip`): the decomp's DUMP_DATA tables and the MP3 decoder's tables are views of the retail data at its Wii address,
read from the player's `main.dol` at start-up (`tools/gametrial/dumptables.py`, `runtime/dolload.cpp`), so
`NiceCrashGame.exe` holds none of it. The package is the launcher, importer, enhance.exe, the game exe,
`build_info.txt` (port commit, decomp pin), `build/fonts`, dtk, the optional upscaler and `LICENSES` (plus the
runtime libraries zig links in: libc++/libc++abi/libunwind, mingw-w64's CRT, compiler_rt); no source, zig or Python.
The tester's readme is `README_PREBUILT.txt`. First run: find → verify → index (seconds), no build. Zip 41 MB with the
upscaler (~16 MB unpacked without it). Clean-profile test 2026-11-23: `--setup` from a `.nkit.iso` in 3.7 s, then the
packaged game off-screen to the save prompt, Create Profile and the name keyboard. The scan (check 3) now also
reads our exes in host byte order and fails on any generated-table run; the old exe fails it.

The rest of this page describes the earlier **source package** (no `--prebuilt`), which is still made the same way:
`tools/gametrial/link.py` builds `NiceCrashGame.exe` on the tester's PC with the bundled toolchain.

`make_package.py` ends with `tools/package/scan_package.py`, and refuses the package if the scan finds anything:

1. no file named like a disc file, and no disc-image/DOL/REL extension;
2. no file with the size and SHA-1 of any file of the developer's own extracted disc (`--disc`);
3. no 32-byte run of `main.dol`'s sections in any file we made. Printable runs are the code's own string literals
   (format strings, names, SDK version strings) and are counted, not failed. Counting patterns are ignored;
4. no initializer in source whose values equal 64+ consecutive words of a `main.dol` data section. Shorter ones
   (vtables, SDK constant tables, a few tuning-float structs) are listed for review: they are code constants of the
   decompiled source. The scan was checked against planted positives: a 64-byte slice of `main.dol` and the
   decomp's `src/sdk_mp3/*.inc` tables (both caught).

`src/sdk_mp3/` is left out of the package: its tables say "Generated by tools/mp3/gentables.py from REXE01 main.dol",
and the port never builds it.

## Tested on this PC (2026-11-17, decomp pin baa703ee4)

## The tester provides

- Their own Excite Truck disc, **USA (REXE01)**, dumped from their Wii: a disc image (.iso, .rvz, .wbfs, .wia, .gcz,
  .ciso) or a Dolphin "Extract Entire Disc" folder. The launcher checks `main.dol`'s SHA-1.
- Windows 10/11 64-bit, a GPU with OpenGL 3.0, ~2 GB free (see the table below), and a few minutes of CPU for the
  build.

## Steps on the tester's side

1. Unzip anywhere with a short path (e.g. `C:\Games\NiceCrash`).
2. Run `Start Nice Crash.cmd` (SmartScreen: More info → Run anyway; the exes are unsigned).
3. Drop the disc image on the launcher. The checklist: find → check it's the USA disc → bundled tools → source →
   unpack and index → **build** → ready. Then PLAY.
4. Problems: Logs page → Save report, and send the folder. Error logs are on by default in this phase
   (`NICECRASH_KNOWN_WORKING_RELEASE 0`); with them off, a crash still writes `logs\crash_<time>.txt`, which the Logs
   page opens for that run and "Copy report" includes.

A console fallback for a failed first run: `build\NiceCrash.exe --setup "D:\path\to\disc.iso"` prints every step and,
on failure, the build log.

## Zip, not an installer (for now)

A zip is the recommendation. Nothing in the package needs installing: there are no services, no registry entries,
no shared runtimes, and every path is relative to the unzipped folder (data goes to `%LOCALAPPDATA%\NiceCrash` and
`%USERPROFILE%\Games\Nice Crash`). An installer would only add a Start-menu entry and an uninstaller, and the
launcher already offers the shortcuts on its last first-run step; "uninstall" is deleting the folder plus those two
data folders. An unsigned setup .exe also draws a stronger SmartScreen warning than an unsigned exe inside a zip.
Revisit an installer when there's code signing or an update host.

## What the tester's PC needs (and doesn't)

| Need | Detail |
| --- | --- |
| Windows 10 or 11, 64-bit | The launcher is x86-64; the game it builds is 32-bit x86 (runs on 64-bit Windows). |
| OpenGL 3.0 | The game renders with OpenGL (framebuffer objects, GLSL 1.20). Any GPU or integrated graphics from roughly 2010 on, with the vendor's driver installed (not Windows' basic display driver). |
| Disk | Measured on the clean-PC test: zip 156 MB, 460 MB unpacked; the unpacked disc 557 MB; build outputs ~120 MB; zig's cache (`%LOCALAPPDATA%\zig`) 117 MB. About 1.3 GB in all (the launcher wants 1.5 GB free before it builds). |
| CPU time | The one-time build: about 7 minutes here at below-normal priority on a busy desktop; longer on a laptop. |
| Vulkan (optional) | Only for "Enhance my game" with the AI upscaler (Real-ESRGAN). Without Vulkan the launcher falls back to Windows' scaler. |
| Media Foundation (optional) | Plays enhanced videos. Present on normal Windows; Windows "N" editions need the Media Feature Pack. |
| Nothing else | No Visual C++ runtime: the launcher, importer and game link only Windows system DLLs (zig/MinGW, static). The bundled Python carries its own `vcruntime140.dll`; Real-ESRGAN's `vcomp140.dll` ships beside it. No Python, zig, git or dtk install: all bundled. No network. |

Disc image formats: dtk (nod) reads `.iso`, `.rvz`, `.wia`, `.wbfs`, `.gcz`, `.ciso` (and `.nfs`), so an `.rvz` from
Dolphin works the same as an `.iso`. Tested here with an `.iso`; `.rvz` goes through the same `dtk vfs cp` path.

## Refreshing the build

The package always ships the pinned decomp (`tools/gametrial/decomp_ref.txt`). For a newer one: agree a pin with
TC, run `tools/gametrial/pin.sh <commit>`, build and play-test the port, then run `make_package.py` again.

## Making a package

```
python -I tools/package/make_package.py --dol "<your main.dol>" --disc "<your extracted DATA folder>" --zip
```

The Python embeddable zip is read from `build/package-cache/python-*-embed-amd64.zip` (download it from python.org
once; without it the package has no Python and the tester needs Python 3.11+ on PATH). `--dol`/`--disc` are only
read, to compare against. `--zip` writes `build/package/NiceCrash-<date>-<port commit>.zip`.

## What the launcher does on a clean PC

- `RepoRoot()` is the package folder (it has `tools/gametrial/link.py`), so the Source step uses the shipped source.
- Tools: `build\tools\python\python.exe` and `build\tools\zig\zig.exe` when both are present (the build gets
  `ZIG=`; `trial.py find_zig` honours it). Otherwise a developer's own: a `python.exe` on PATH must answer a version
  probe (Windows' Microsoft Store stub doesn't), and zig from `ZIG`, PATH or winget.
- dtk: `build\tools\dtk\dtk.exe` first, the matching repo's copy only in a source checkout.
- The build reads only the pinned export: `sdkbuild.py` and `hbmbuild.py` no longer read the live `excite-truck`
  checkout or call git (the pinned `libs/msc` and `configure.py` are in the export; identical to live today).
- Data: settings and logs in `%LOCALAPPDATA%\NiceCrash`, the unpacked disc in `launcher.data_dir`
  (`%USERPROFILE%\Games\Nice Crash`), zig's global cache in `%LOCALAPPDATA%\zig`.

Testing a clean install on a developer PC: copy the package outside the repo and run `--setup` with
`LOCALAPPDATA`, `NICECRASH_LAUNCHER_DATA_DIR` and `NICECRASH_SHORTCUT_DIR` pointed at a scratch folder and PATH cut
down to Windows' own folders. For any boot check (`--launch-game`), also set `NICECRASH_HIDEWINDOW=offscreen` and
`NICECRASH_DISPLAY_WINDOW_MODE=windowed`: a scratch install defaults to borderless full screen and would cover the
developer's monitor. Offscreen still renders, so `NICECRASH_SHOT=<retrace>:<file.bmp>` works.
